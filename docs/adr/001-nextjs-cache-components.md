# ADR 001: Adopt Next.js Cache Components (16.x) as the rendering model

## Status

Accepted

## Context

`create-next-app@latest` on Next.js 16.4.0 scaffolds new apps with Cache
Components (`cacheComponents: true`) and Partial Prefetching
(`partialPrefetching: true`) enabled by default. This is a materially
different rendering model from pre-16 Next.js:

- Reading `cookies()`, `headers()`, `searchParams`, or calling
  `Math.random()`/`Date.now()`/`crypto.randomUUID()` outside a `<Suspense>`
  boundary or `"use cache: private"` scope is a **build error**, not a
  runtime warning.
- A page is split into a prerendered **static shell** (everything cacheable
  or static) plus **streamed** sections (anything that reads the request).
- `usePathname()` / `useSearchParams()` in a Client Component used outside
  `<Suspense>` blocks prerendering for the same reason.

This was hit directly (and fixed reactively) while building a separate
demo UI earlier in this project: a server component called `Date.now()`
directly, and a nav component called `usePathname()` without a `Suspense`
boundary. Both failed `next build` with "blocking prerender" errors. Given
this app is auth-heavy and RLS-scoped from M2 onward (every real page reads
the signed-in user's session), hitting this same class of error on every
authenticated route would be expensive to fix one at a time.

## Decision

Keep Cache Components enabled (the default) rather than disabling it to get
the older, more familiar rendering model. Design every route against it
from M2 onward using the patterns Next's own authentication guide
documents:

1. **Session reads use `"use cache: private"`**, never a plain
   `"use cache"` or a bare `await cookies()` at a layout's top level.
   `lib/auth.ts`'s `getCurrentUser()` is the one place that reads the
   session; nothing else re-reads `cookies()` directly. This is the Data
   Access Layer pattern the guide names explicitly — it also satisfies our
   spec's rule 5 (secrets/session data never leak into the wrong layer) by
   construction, since there's one audited chokepoint instead of N.
2. **Every component that reads the session sits behind its own
   `<Suspense>` boundary**, pushed as far down the tree as possible (never
   at the layout's top level) so the rest of the page — nav, sidebar, static
   chrome — still prerenders into the static shell and loads instantly.
3. **Authorization is re-checked server-side in every Server Action and
   Route Handler**, never inferred from what the client was shown. This is
   the guide's explicit warning ("Trusting the client for authorization")
   and is also required by our spec's RLS model (rule 6) — a UI check hiding
   a button is not a security boundary, the RLS policy and the
   security-definer RPC are.
4. **Org/brand-scoped data fetches follow the session-derived-data pattern**:
   resolve the user server-side, pass only the stable id (`org_id`,
   `user_id`) into a plain `"use cache"` function, never the raw session or
   cookie. Keeps cache keys safe (cache keys/tags are stored in plain text —
   never key or tag on anything sensitive) and keeps the unexported inner
   function un-callable with an arbitrary org id from outside its own
   module.
5. **New routes are migrated onto this model immediately**, not deferred
   with `export const instant = false`. That escape hatch exists for
   migrating legacy apps; this is a greenfield build, so there's no legacy
   render path to preserve.

## Consequences

- Every page/layout that touches `org_id`-scoped data needs a `<Suspense>`
  boundary somewhere in its tree; this is non-optional, not a style choice.
- `apps/web/node_modules/next/dist/docs/` is the authoritative reference for
  this Next.js version — training-data knowledge of "classic" Next.js
  data-fetching patterns (e.g. unconditional `cookies()` in a Server
  Component, no Suspense) will produce build errors here. Check the docs
  folder before writing a new data-fetching pattern, not after the build
  fails.
- `apps/web/AGENTS.md` is auto-regenerated by `next dev`/`next build` and is
  intentionally committed, not gitignored — removing it from a diff only
  recreates the uncommitted change on the next dev run.
